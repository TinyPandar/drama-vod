# 决策记录

本文件从 2026-11-15 起记录产品与协作决策。此前各阶段的方案写在对应分支的 README 里，这里不补写或改写那些历史决定。

## 2026-11-15 管理控制台改版方向与协作边界

**决定**

- 管理控制台这一轮先做界面改版，做成标准后台：左侧一列导航切页，右侧展示内容。登录页独立，登录后再进入这套布局。
- 导航分组已定：管理端为「租户与 Key」「模板」；租户端为「资产」「任务」「Webhook」「用量与配额」。当前页要高亮。右侧页头要能看出当前管理员和已选用的租户上下文，但不展示 Key 明文。
- 现有管理功能和租户功能都保留，不因改版丢失（上传与续传、取消 / 重试 / 重转、试播、Key 明文只显示一次等）。
- 未登录、未选 Key、Key 过期或失效时，页面给出明确说明和正确入口，不要把接口返回的 `unauthorized（401）` 当作主要提示。前端引导不能绕过服务端权限。
- 不改后端接口、鉴权与数据模型，不改旧「短剧场」播放页，不在本轮扩展 OAuth、完整 RBAC 或新业务。
- 本轮在 `plan/console-redesign` 只提交需求文档（README 分支方案和本决策记录）。界面视觉方案由 Fable 出，Frank 拍板；开发仍由 Frank 自行驱动 Claude 在该分支进行。没有 Frank 的明确指令，不自动启动设计或开发。
- 配色、字体家族、是否使用现成 UI 组件库等视觉与技术选型，Frank 尚未选定，不能写成已批准。（本条记录时的状态；同日确认见下一条。）

**原因**

- 检查现有控制台时，入口挤在顶部一行，看起来简陋；管理员登录后进入资产页，权限模型（管理登录与租户 Key 分开）没有被界面讲清楚，容易直接看到 401。
- Frank 明确要求先把后台整理成标准的左右布局，并按既有流程从 `main` 开分支、把需求写进该分支 README，而不是只在聊天里贴一段说明。
- 视觉方案交给 Fable，避免在需求里擅自指定配色或组件库；实现仍按既有分工，需求文档不写业务代码、不写技术设计，也不在这一步直接委派设计或开发。

**排除**

- 不把这一轮做成功能扩展或后端改造。
- 不把只出现在聊天里的说明当成已经落盘的需求。
- 不把未拍板的配色、UI 库或实现架构写成既定方案。

**未定**

- 配色、字体家族、圆角和装饰风格。
- 是否引入现成 UI 组件库、用哪一套。
- 侧栏在窄屏上的具体收纳方式。
- 「短剧场」入口在控制台里的具体位置。
- 除已定侧栏分组以外的其他视觉细节。

以上是本条记录时的状态。同日稍后 Frank 已确认 Fable 设计稿，对应未定项以下一条为准，不再把本条「未定」当作当前结论。

## 2026-11-15 Frank 批准 Fable 设计为实现基准

**决定**

- Frank 审阅 `docs/console-redesign/` 的设计预览后表示「风格可以，按这个做」。该稿成为把改版落到真实 Vue 控制台的实现基准：沿用预览，不另外扩做深色模式。
- 已确认的视觉与交互约定：
  - 浅色后台，主色靛蓝 `#3451D1`（同时代表管理登录），租户 Key 用青绿 `#0B7A75`，两种身份全程用颜色加文字区分。
  - 系统字体（苹方 / 微软雅黑 / Segoe UI），不加载外部字体；不引入大型或现成 UI 组件库。
  - 窄屏侧栏收成左侧抽屉（设计稿以宽度不超过 860 为收纳点）；「短剧场」入口放在侧栏最底部，标注「旧播放页」，不改旧播放页本身。
  - 状态用中文徽标，并在旁边保留接口原值（如「可播放 READY」）。
- 此前上一条及 README「尚未拍板 / 等 Frank 确认的事」里的对应未定项，以此条为准，视为已确认。
- 下一步是在本分支 `plan/console-redesign` 把已批准样式接入 `console/` 下现有控制台，覆盖全部已有页面与功能，走真实接口，而不是再出一套静态稿。开发仍由 Frank 自行驱动 Claude；没有他的明确指令，不自动启动实现，不合并到 `main`。

**原因**

- 设计预览已按先前确定的侧栏结构给出登录、租户与 Key、资产列表和统一规范；风格确认之后，实现阶段不应再把配色、字体、组件库、窄屏收纳和短剧场位置当作未选项。
- 预览稿没有做深色模式，Frank 要求按这个做，因此不额外扩展深色。

**排除**

- 不把静态设计稿本身当成已经落地的产品界面。
- 不借风格确认重开视觉方向，或改回原来的黑金色。
- 不在确认风格的同时改后端、加新业务或扩展权限系统。

**未定**

- 样式如何接到现有 `console/`（模块怎么拆、公共部件怎么抽等）由实现者用 pstack 的 architect 出至少两套、对齐现有前端的方案，Frank 拍板后再写代码。若方案要新增依赖、改变产品行为或改后端，仍须先问 Frank。
- 选用 Key、模板、任务、Webhook、用量、资产详情等页面没有单独设计稿，实现时沿用已确认的同一套规范，不另开视觉方向。

## 2026-11-18 按 A → B → C 推进下一阶段

**决定**

- 用户要求把下一阶段路线里的 A、B、C 三段都做完：A 是在整套 Compose 栈上真跑此前各阶段没跑过的检查（含控制台真实后端验收）并接进 CI；B 是资产生命周期（删除、孤儿对象与僵尸上传清理、Webhook 记录保留期、资产元数据与搜索）；C 是让短剧 Demo 真正成为 Core 的客户（Demo 用户登录、付费集走 Core 加密资产、iPhone 原生播放、收掉旧转码与播放链路）。
- 三段各开一个分支、各自在 README 写分支方案和实现说明，沿用既有协作规则：不合并到 `main`、不 force-push、不把密钥写进仓库。分支依次叠起来：`plan/live-verify`（A，从 `main` = `c102205`）→ `plan/asset-lifecycle`（B，从 A）→ `plan/demo-on-core`（C，从 B），合并时按 A → B → C 的顺序。
- 开发机没有 Docker：用 colima + Docker CLI 的独立二进制放在仓库外的 `.phase3-tools/dockerkit/`，不装进系统，和此前 MinIO、MySQL、JDK 的做法一致。

**原因**

- 此前每个阶段的「没跑」清单都卡在开发机没有 Docker 上；不先在真实栈上跑通，B、C 的改动就没有可靠的回归基线。
- 叠分支而不是三条并行分支：A 修掉的问题和新增的验收脚本 B、C 都要用；三段都在 README 顶部加章节，并行分支合并时必然冲突。

**排除**

- 不借这一轮重写 Worker、换消息队列、改消息 v1，不做 DRM / KMS / 多 CDN / 微服务拆分。
- 不把 E（运营与安全）、D（开发者体验）、F（媒体进阶）里的内容塞进这三段。

## 2026-11-19 路线 C 改变 Phase 0 冻结的 Demo 接口语义

**决定**

- Demo 拆成视频云的客户之后，`upload-url` / `complete` / `GET /api/assets/{id}` 落到 Core，`asset_id` 变成 Core 资产 id、源对象键换成 Core 的键；`play` 的观众改由 Demo 会话决定，`?user_id=` 不再单独算数，匿名看付费集新增 401；`unlock` 要本人会话并扣金币。逐条写在 `docs/phase-0-contract.md` 末尾。
- 旧 Demo 转码链路默认停用，旧读接口保留到切换前发出的地址过期；已有旧剧集用迁移工具搬到 Core。
- 保留过渡开关 `DEMO_ALLOW_USER_ID_PARAM`（默认关）和 `WORKER_LEGACY_ENABLED`（默认关），只用于切换期。

**原因**

- Phase 0 文档本身就写明这些条目要冻结到「Demo 改完」「Demo 拆出去」为止；路线 C 就是这一步。不改语义就只能让 Demo 继续绕开视频云，或继续让任何人凭 `user_id` 看付费集。

**排除**

- 不做真实支付、充值、找回口令；不在这一步删除旧原片和旧 HLS 产物。
