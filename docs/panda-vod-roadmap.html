Project blueprint · 2026.11

Panda VOD

面向开发者的视频云服务平台

将现有短剧点播 MVP 演进为可复用的视频基础设施：统一提供上传、媒体资产管理、异步转码、存储、播放授权与分发能力。短剧站作为第一个业务 Demo 和内部客户。

Java 21 · Spring BootPython · FFmpeg WorkerMySQL · Redis · RabbitMQMinIO · Nginx · HLS

01. 产品定位

不要把项目只做成一个“能播放短剧的网站”，而是把它拆成视频云核心能力 + 短剧业务示例。

Panda VOD Core视频云基础设施。面向开发者提供 API、资产管理、转码、播放授权、回调和用量统计。
Drama Demo短剧业务应用。负责剧集、付费解锁、内容展示和业务页面，通过 API 调用 Panda VOD。
关键边界：Drama / Episode 是短剧业务概念，不应该成为 VOD Core 的核心领域模型。核心平台只需要理解 Media Asset（媒体资产）。短剧的一集关联一个或多个媒体资产即可。

短剧当然属于视频内容平台；这里的“短剧平台”和“视频云”不是竞争关系：前者是业务产品，后者是底层视频能力服务。VOD（Video on Demand）描述的是点播交付模式，不限定视频时长或内容类型。

02. 核心架构决策

决策建议原因
服务形态模块化单体 + 独立 Worker早期降低部署和联调成本，同时保留清晰领域边界；暂不拆微服务。
控制面Java 21 + Spring Boot承载租户、鉴权、资产、任务编排、播放授权、回调和管理 API。
媒体执行面保留 Python + FFmpeg已有转码链路可复用；重计算工作由 FFmpeg 完成，没必要为语言统一而重写。
事实来源MySQL任务与资产状态以数据库为准；消息队列不是业务状态数据库。
异步通信RabbitMQ负责唤醒 Worker、投递事件；消费者必须支持重复消息和幂等。
对象存储MinIO（后续兼容 S3）原片与转码产物放对象存储，数据库只保存对象元数据和引用。
不建议现在做：一上来拆成十几个微服务、引入 Kubernetes、重写 Python Worker、做 DRM 或多 CDN。先把单租户到多租户的核心链路做扎实。

03. 推荐技术栈

层次技术职责 / 说明

06. API 设计草案

统一前缀 /api/v1，使用资源导向命名；管理端 API 与租户 API 分开授权。

方法 / 路径用途
POST /uploads创建上传会话，返回 presigned URL 或 multipart 信息。
POST /uploads/{id}/complete通知上传完成；服务端 HEAD 校验对象后创建转码任务。
GET /assets分页查询当前租户媒体资产。
GET /assets/{id}查看资产状态、媒体信息与可用播放版本。
POST /assets/{id}/transcodes使用指定模板发起转码。
GET /jobs/{id}查询任务状态、进度、失败原因。
POST /assets/{id}/playback-token签发短期播放授权。
POST /webhooks注册转码成功/失败等事件回调。
GET /usage查询租户用量和配额信息。

幂等性：创建上传会话、发起转码等写接口建议支持 Idempotency-Key。客户端重试不能意外创建多份任务。

07. 异步转码任务：项目最值得做深的工程点

目标不是喊“Exactly Once”，而是做到至少一次投递 + 幂等消费 + 可恢复状态机。

  1. 数据库事务创建任务与 Outbox 事件同一事务
    上传完成校验后，在同一个 MySQL transaction 中写入 transcode_job 和 outbox_event，避免“任务已入库但消息没发出去”。
  2. Outbox Publisher 可靠发布后台循环
    发布到 durable queue，使用 publisher confirms；成功后标记事件已发布。发布器崩溃可重发，因此下游必须幂等。
  3. Worker 按 job_id 查询并 Claim消费端
    消息只携带 job_id 与 schema_version。Worker 从 DB 原子领取任务，不直接相信消息中的任务状态。
  4. Lease + Heartbeat + Fencing Token执行期间
    Worker 定期续租；每次 claim 递增 claim_version。旧 Worker 即使租约过期后恢复，也不能提交过期版本的结果。
  5. 临时输出目录 + 完成后原子切换提交结果
    先写入 job 专属 prefix，校验 playlist 与分片完整后，再通过事务把资产切为 READY。避免客户端看到半成品 HLS。
  6. 退避重试与死信故障恢复
    区分可重试与不可重试错误；指数退避加 jitter，超过次数进入 FAILED / DLQ，保留错误码和日志定位信息。

建议任务状态

PENDING → QUEUED → RUNNING → SUCCEEDED；失败可进入 RETRY_WAIT 再回到 QUEUED，不可恢复则 FAILED，用户取消则 CANCELLED。

08. 安全与生产化清单

  • API Key 只存哈希；支持 scope、过期、撤销和轮换，创建时仅展示一次明文。
  • 管理端使用 Spring Security + JWT 或安全 Session + RBAC；租户 API 与管理 API 权限隔离。
  • MinIO Bucket 默认私有；由服务端签发短时上传 URL，播放通过短期 token / 签名 URL 授权。
  • 上传校验对象归属、文件大小、MIME、扩展名、配额；不能只信任客户端声明。
  • FFmpeg 使用参数数组执行，不拼接 shell 字符串；限制 CPU、内存、时长、磁盘和并发，隔离不可信媒体输入。
  • HLS Key 不明文暴露；生产环境使用 KMS / 信封加密。开发环境也应抽象 KeyProvider，不把密钥硬编码进代码仓库。
  • Webhook 防 SSRF：拒绝 localhost、内网、云 metadata 地址；处理 DNS 重绑定，限制 HTTPS、超时、重试和响应体大小。
  • 播放 Key API 做鉴权与限流；敏感响应禁止被公共缓存。
  • 播放计数不能简单 GETDEL 后直接写 DB，否则 DB 故障可能丢增量；采用可恢复事件/持久化缓冲与幂等回刷。

09. 开发路线图

按每周约 15–20 小时估算；时间是工程计划区间，不是硬承诺。优先保证每个阶段都有可演示的验收结果。

  1. Phase 0 · 契约与边界冻结2–3 天
    梳理现有 API、表结构、MQ 消息和 Worker 行为；定义 OpenAPI、消息 JSON Schema 与版本号；写关键 contract tests。先确定哪些旧接口需要兼容。
  2. Phase 1 · Spring Boot 骨架约 1 周
    建立 Java 21 + Spring Boot 模块化单体；接入 MyBatis-Plus、Flyway、Spring Security、Actuator、Micrometer；统一异常响应、参数校验、日志、request-id、配置管理。先迁移健康检查和只读接口。
  3. Phase 2 · 上传与资产主链路1–2 周
    实现 tenant（初期可单租户）、API Key、upload_session、storage_object、media_asset；完成 presigned upload → complete → HEAD 校验 → 创建 job/outbox。Python Worker 继续消费兼容消息。
  4. Phase 3 · 转码任务可靠性1–2 周
    实现 Outbox Publisher、幂等 Claim、租约续期、fencing token、退避重试、取消和 DLQ；修复小分辨率 ladder 不应被放大的问题；补充 Worker 多实例和故障注入测试。
  5. Phase 4 · 播放与分发1–2 周
    MinIO 私有桶、播放 token / 签名 URL、Nginx 回源鉴权、HLS playlist 与分片访问、缓存和 CORS；补充首帧时间、播放失败、卡顿等 QoE 指标。
  6. Phase 5 · 平台化控制台2–3 周
    Vue 3 控制台：租户、API Key、资产列表、上传、任务详情、转码模板、Webhook、用量统计；实现 webhook 签名、重试、限流与基础配额。
  7. Phase 6 · 高级媒体能力长期迭代
    断点续传 / Multipart、截图与缩略图、字幕/音轨、CMAF/fMP4、H.265/AV1、多对象存储适配、多 CDN、生命周期与冷存储。DRM 放到有明确需求后再做。
4–6 周目标：Java API → Python Worker → MinIO → HLS 播放，端到端闭环。
8–12 周目标：可演示的平台版本，具备多租户、可靠任务、控制台、Webhook 与监控。

10. 第一版验收标准

  • 租户 A 无法读取、修改或播放租户 B 的资产。
  • 浏览器或脚本可通过预签名 URL 直传视频，不经过 API 服务中转大文件。
  • 上传完成后任务可靠创建；API 重试不会重复创建转码任务。
  • Worker 重复收到消息、进程被 kill、租约过期、MinIO 短暂不可用时，任务能恢复或明确失败。
  • 只有所有 HLS 产物验证完成后，资产才进入 READY。
  • 过期或伪造的播放 token 无法访问受保护内容；私有对象不能被匿名直读。
  • Drama Demo 能通过 VOD API 完成上传、转码、播放，付费解锁仍由 Demo 业务层控制。
  • Prometheus 能观测 API 延迟、任务积压、转码耗时、失败率和 Worker 存活状态。

11. 后续演进与项目展示重点

值得优先展示的工程能力

  • 可靠异步任务：Outbox、幂等、租约、fencing token、重试和死信。
  • 多租户安全：tenant scope、API Key scope、资源隔离和权限测试。
  • 对象存储直传：预签名上传、校验、Multipart 扩展。
  • 媒体处理链路：FFmpeg 多码率 HLS、模板化转码、失败诊断。
  • 可观测性：任务吞吐、队列积压、转码耗时、播放 QoE 和成本指标。

明确暂缓

微服务拆分、Kubernetes、复杂计费、DRM、多 CDN、多区域调度。先做出一套边界清楚、稳定可靠、能让第三方开发者调用的 API。

最终项目叙事：我实现了一个面向开发者的视频云平台，采用 Spring Boot 控制面与 Python/FFmpeg 媒体执行面分离架构，支持对象存储直传、多码率异步转码、HLS 安全分发、多租户隔离和可靠任务调度；并用短剧 Demo 验证完整业务闭环。
